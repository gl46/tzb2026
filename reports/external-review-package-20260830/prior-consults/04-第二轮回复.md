## 总结论(ChatGPT)

**训练线选择顺序:D ＞ C ＞ B ＞ A。**

1. 立即封存当前可交付版本;救援实验一律独立分支+新实验身份。
2. 用不超过 8 小时做一次有硬停止条件的 B 类 headroom 探测。
3. 探测通过才做完整确认实验;任一门未过,立刻退回 C(不再追微调分数,集中强化演示、契约评测与材料)。
4. **不要直接做 A(随机 5–10 倍扩量)**——没有证据表明剩余错误源于数据不足。
5. 比 A/B 都高收益的动作:在新版本演示支路给 TCP/frame 自洽检查限定 **2 小时**;若 95.3mm 真是固定 TCP 偏移,修出一个诚实标注 vNext 的成功抓放镜头,对评审价值远高于 LoRA 多几个百分点。

## 48 小时决策树

**第 0 步|保护现有成果**:release tag 固化 few-shot 部署版+演示+配置+工件哈希;救援用独立分支与 artifact identity;失败不合并;冻结前留 ≥12h 只做 smoke 与取证。

**第 1 步|用现有 logits 判断 A 是否还有信号(不训练,几十分钟)**:对开发集算 margin = logit(正确) − max_{k≠y} logit(k),比较 LoRA vs few-shot base,重点看 base 答错的 14 例。探索门(全过才准 A 进候选):≥10/14 错误案例正确答案 margin 向正移动;正确案例无普遍恶化;NLL 或 Brier 明确改善;错误可归入一个可生成可复现的具体切片。不满足 → **直接淘汰 A**。满足也先做 512 条目标切片微型实验,不直接生成 6000 条。

**第 2 步|只筛两个新任务**

- **第一候选:分区条件精确计数**("第三格内蓝色螺栓几个")。参数:数量 0–9 或 1–10;类别数量均衡;有非目标干扰物;部分样本相邻区域只差 1;物体清晰可见(不用严重遮挡人为压低准确率);输出固定单 token 选项,保持 selected-logit CE。理由:近期受控研究显示 VLM 精确计数即使在简单场景仍易失败,计数证据可能在视觉投影阶段存在却被语言层低估;组合空间基准也发现计数弱点限制多步空间推理——语言侧 LoRA 有可能学会更稳定地利用已有视觉证据。
- **第二候选:粗粒度姿态分箱**(4–5 类离散:直立/轻度倾斜/明显倾斜/侧倒/倒置)。要求:视觉不对称零件;分类边界留缓冲带(不生成正好 20° 边界样本);GT 角度只用于标签,人工抽查图像是否真可辨;输出固定选项 token。风险:若单张 RGB 姿态信息本身不足,语言侧 LoRA 也救不了。
- **第三候选:多步空间状态更新**(先移 A 再移走 B,哪区最多)。易暴露 few-shot 短板但叠加计数+绑定+状态更新+比较,未必能被小规模 LoRA 改好;适合第二轮,不适合本轮唯一下注。
- **不建议:长 JSON 技能计划微调**。当前损失只对选项 token 计 CE,与长序列学习不匹配,要改损失/解析/协议,冻结前风险过高;且 Qwen-VL 系列本就以结构化输出见长,headroom 预计小。长 JSON 应继续作为**契约合法率指标**而非 LoRA 救援任务。

**第 3 步|headroom 快速筛选**(不用"低于 60%"一刀切;50 例在 60% 附近标准误 ≈7pp,只够粗筛):每候选用 16 例 prompt calibration + 64 例独立 screening(≥8 家族×8 例),同时跑 zero-shot、2-shot、blank-image/shuffled-image 对照。

进入微型训练的门(4 分类为例):人工可判定 ≥19/20;few-shot 准确率落在 **40–70%**(太高无 headroom,接近随机则可能视觉不可解或标签设计有问题);shuffled-image 后至少掉 10pp(证明确实用图);错误分布 ≥4 个家族;错误非单一类别/模板造成;输出解析成功率 ≥95%。10 类精确计数可调整为:高于随机 ≥15pp 但低于约 70%。正确标准是"**存在足够 headroom,同时任务仍可见、可学,且模型已在使用图像**"。

**第 4 步|512 条微型 learnability probe**(仅对通过筛选的第一名):训练 512 episode(≥16 家族),pilot eval 96 episode(≥12 未见家族);沿用 r=8/lr=2e-5/2 epochs,**不搜索** rank/lr/target modules;base 与 LoRA 完全相同 prompt/示例/解码/解析器。

硬门(全过才进正式):成对准确率净改善 ≥+10pp;修正数 ≥2× 回归数;无主要类别下降 >10pp;blank/shuffle 对照仍表明依赖图像;改善出现在多个家族。任一不过 → **停止训练路线执行 C**,不要再试 r=16/三种 lr/五个 epoch。

**第 5 步|正式确认实验最低规格**(约 3000 episode):

| 划分 | Episode | 独立家族 | 用途 |
| --- | ---: | ---: | --- |
| Train | 2400 | ≥40 | 固定训练 |
| Dev | 240 | ≥12 | 只选 checkpoint |
| Confirmatory test | 300 | ≥30 | 单次读取、主声明 |
| Human blind | 72 | ≥12 | 外部方向验证 |

设计:每 episode 最好只产一个主 QA(减少同图相关性);最终测试的 family id 与 seed 列表在训练前提交 hash;测试集只读一次;primary metric 只设一个;exact McNemar 用于 episode 级成对;cluster bootstrap 以生成器家族为单位;报告 test 与 blind 方向一致性;不得把 300 episode 当 300 完全独立样本,须同时披露 30 个家族。

结论分级预注册:**可作正面结果**=test 成对 ≥+10pp 且 cluster-bootstrap 95% CI 下界 >0 且 blind 不为负且格式/拒绝/安全契约无明显退化;**只能称方向积极**=+5~+10pp 但区间跨 0,或 test 改善 blind 未复现;**仍是无收益证据**=<+5pp、只改善格式、改善集中在极少数家族、或 blind 明显回归。

**如何预防再次被近重门全灭**:不要为让 pHash 通过而故意改变目标分布(固定机位若是部署设定就保持)。应改的是数据身份设计与检测方式——渲染前先建 `family_id = 资产集 × 布局 × 数量制式 × 材质光照 × 干扰物`,按 family 原子分 train/dev/test,各 split 用不同 seed namespace,模拟器 manifest 作主 lineage 证据,视觉近重检测只作跨 split 泄漏审计,固定背景优先用 instance mask/depth/前景差异而非全局低频 pHash。全量生成前做 200 图 instrument preflight:抽样跑完整近重图构建,检查跨 family 桥边,估算最终 test 是否还能保留 ≥24–30 个独立家族;若预测坍缩,停止当前数据身份、修复设计后重注册(这是实验前验证仪器,不是运行后调阈值)。

## "微调打平"的三种正面但不夸大说法

- **技术评审版**:在冻结的 67 个成对评测案例中,LoRA 相对调优后 2-shot 基线主指标净变化为 0。训练 CE 从 0.321 降至 0.179,说明优化链正常,但训练内改善没有转化为外部增益。我们因此按预注册规则部署无 adapter 的 few-shot 配置,而没有把训练损失下降误报成能力提升。
- **非专业评审版**:我们让 few-shot 和微调在完全相同条件下公平对决。微调没有多答对一题,因此系统选择了更简单的 few-shot 方案。这个结果说明我们不仅会训练模型,也会用证据判断一个训练模块是否值得上线。
- **路线图版**:573 条可审计数据已打通生成、去重、训练、重载、成对评测与自动回退的完整闭环。本轮表明当前任务下 adapter 没有额外价值,下一轮资源应转向具有明确视觉 headroom 的精确计数与空间组合任务。

**两句不许说**:"两示例 few-shot 已达任务天花板"(只有 78 例开发集、2/3 个聚类,无法证明);"收益会随数据规模自然释放"(没有 scaling curve,只能是待验证假设)。**可以说**:当前数据规模、任务和冻结配置下,没有观察到 adapter 的增量收益。

## 评审问"训练是不是白做了"

> 如果目标是让这次部署准确率提高,那么这个 adapter 确实没有创造增量,所以我们没有上线它。但这项工作并非被包装成成功:它验证了数据门、训练、重载、成对评测和自动回退整条链,也防止了我们把训练损失下降误写成模型能力提升。它产出的是一个被严格检验并否定的假设,以及一套以后可以直接扩展的数据和训练基础设施。

短口头版:**对本轮准确率它没有价值;对系统工程,它证明了我们能识别并淘汰一个无效模型,而不是因为训练过就强行部署。**

## 问题二|PPT 结构(8 页主 deck + 3–4 页附录)

总原则:两个阴性只占**一张**主页面(详细统计各放附录);主页面顺序=先看见系统能做什么→看懂架构为何不同→看见正面保留评测→最后才是严格探针发现了什么;不用"训练、抓取都失败"开场,也不暗示已通过完整抓取成功率验证。

1. **可运行的多模态工业智能体**:标题"让大模型理解任务,让可验证执行层约束动作";放 8–12 秒循环(场景图+指令→JSON 技能计划→执行/拒绝/恢复);三标签=多模态指挥体/符号技能契约/双层失败恢复。**不放** 95.3mm、0pp、573 行。
2. **一条自然语言指令如何进入机械系统**:用一条真实指令贯穿(放入第二排第三格),横向展示场景图→指挥体解析→实际 JSON→技能序列→执行日志;金句"自然语言不会直接驱动关节,必须先通过结构化契约和执行前置条件"。
3. **大脑与小脑分工**:左=图像理解/指令消歧/目标绑定/任务分解/任务级重规划;右=IK/碰撞/轨迹/接触门/技能前后置条件/局部 fallback;底注"大模型不能绕过 IK、碰撞或接触门;经典执行器也不负责理解开放语言"。
4. **失败如何被恢复**:真实事件时间线(计划→前置检查→候选1 被拒→切候选2→仍不可执行→升级指挥体→重分解或安全拒绝),嵌故障恢复视频;若用故障注入必须标注"确定性故障注入:目标格位占用",不得伪装成自然发生。
5. **部署指挥体的独立保留评测**:只放保留族群数字("部署配置:2-shot,no adapter;独立保留族群 x/N=y%;单次运行|全分母|零重试|未参与训练与提示调优"),再分三类(场景状态判断/空间区域判断/指令到技能契约)。**不在这里放 LoRA 的 0pp**。
6. **严格探针定位了两处当前边界**(左右两栏):左=执行层存在性探针,**必须用完整冻结分母 s/12**(0/12 就写 0/12),下方注明"5 次可比较接触误差测量全部失败、最佳 95.3mm、门限 20mm、未提供成功率≥75% 的证据、首要排查 TCP/frame 固定偏移";右=微调增益探针(573 行、CE 0.321→0.179 即 −44.2%、67 例成对、增量 0pp、盲测 45 例零逐例回归、部署 2-shot 无 adapter),小字注明"测试/盲测仅 2/3 个独立聚类,区间不稳定;格式与边界判断各净改善 1 例,不改变主结论"。页底"严格评测没有制造成功,而是把瓶颈分别定位到执行几何和任务适配 headroom"。
7. **为什么这些结果反而说明系统可信**:治理时间线(数据方案 v1→仪器退化全量阻断→v2/v3 阴性预注册→v4 通过全部门→训练与成对评测→自动选择无 adapter 部署)+四个数字(≈30 次不合规运行/工件被 fail-closed 拦截、3 份预注册阴性如实保留、0 条评测污染进入训练、关键工件全部 hash 与版本身份绑定)。"几小时内两个周期"要写成"完成 2 轮'发现→阻断→修复→复审→重新点火'的版本化闭环",而非"我们修 bug 很快"。
8. **当前交付与下一版**:左=可运行指挥体/JSON 契约/经典规划执行接口/双层恢复/审计与预注册基础设施/独立保留评测;右=TCP-frame 自洽与固定偏移修复、最后 40–60mm 闭环接近、测试集 ≥24–30 个独立家族、对精确计数做有 headroom 的适配、新结果独立重注册。结尾"我们的目标不是只保存成功录像,而是让系统知道何时能执行、何时应恢复、何时必须拒绝"。

**30 秒标准答案**:我们交付的是一套在 Isaac Sim 中可运行的工业智能体:大模型把图像和指令转成结构化计划,经典执行层负责受约束动作和两级失败恢复。严格测试发现抓取与微调仍有边界,因此我们没有强行上线无效模块,而是让成功、拒绝和失败都可验证、可追溯。

## 五天内低成本高显示度加分件

1. **90–110 秒主视频**:0–8s 最终效果先行;8–25s 正常路径;25–42s JSON 契约字段与前置条件叠加;42–65s 确定性局部失败与执行层 fallback;65–80s 升级指挥体重分解或安全拒绝;80–98s 证据卡(保留评测、67 例成对、95.3/20mm);98–110s "能执行、能拒绝、能恢复、能追溯"。少放终端滚动,多用放大的事件卡。
2. **技能审计 HUD 叠加**:每步只显示当前技能/前置条件(通过·拒绝)/执行结果/下一动作(局部恢复·升级指挥体)——比再做一个新模型更容易让非专业评委看懂架构创新。
3. **36–48 例契约能力测试**:1/3 正常可执行、1/3 明确不可执行(目标不存在/格位占用)、1/3 歧义冲突;报 JSON schema 合法率、execute/refuse/escalate 路由正确率、技能前置条件合法率、不可执行安全拒绝率。直接测量真正的创新点且不依赖 TCP bug;若保留集已覆盖则同数字下分层报告,不造第二套重复准确率。
4. **两种工程范式对照页**(不写"我们 vs 对手"):自由文本直接转动作 vs 先生成 JSON 契约;可执行性隐含 vs IK/碰撞/前置条件显式门控;失败后整段重启 vs 技能级恢复再任务级重规划;主要展示成功案例 vs 全分母预注册与失败留痕。页脚注明这是工程范式对比,不代表所有端到端系统都缺少安全或评测机制。
5. **只读证据包入口**(二维码/链接):一次完整 run 的事件日志、预注册摘要、manifest/hash 摘要、一段正常路径、一段恢复路径、一段被门拒绝的失败路径。不要让评委面对几十个文件自找证据。

## 问题三|保留评测 headline 呈现

- **>80%**:可作主要正面数字,但标题必须准确写"部署配置在未参与训练与提示调优的保留族群上:x/N,y%",不写"模型总体准确率";若只有一个保留族群,加注"保留族群内一次性估计,不代表跨族群总体性能"。与"微调打平"不冲突——两个数字回答不同问题(保留准确率=最终 few-shot 部署系统多强;0pp=adapter 在同一系统上有无额外价值),可写成"部署性能 y%;adapter 增量 0pp;因此选择更简单的无 adapter 配置"。
- **60–75%**:**仍然要放**,但不放封面大字,也不称"保守估计"(除非"该族群更难"在看结果前就定义并验证过)。表述"独立保留族群上的一次性外部估计:x/N,y%;全分母、零重试",同时显示分母、任务类别分解、(仅当基线定义已冻结时)多数类或随机基线、主要错误类型、聚类/家族数量。标题用"保留族群揭示的部署能力与边界"。
