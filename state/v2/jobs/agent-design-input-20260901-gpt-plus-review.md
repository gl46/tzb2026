## 先给结论

这道题不应该做成“找一个最强多模态大模型，看一张图后直接吐机械臂动作”。

更合适、也更接近工业落地的方案是：

> **证据驱动世界模型 + 大模型高层规划 + 行为树/技能库执行 + 每步验收 + 双层失败恢复**

其中：

* 多模态大模型负责理解指令、理解语义歧义、生成目标和重规划；
* 专用感知模块负责实例、位置、6D 位姿和正常/倒放/倾倒等状态；
* 行为树负责把任务变成可执行、可中断、可恢复的流程；
* 机械臂控制器只执行有限的、经过验证的技能；
* 每一步完成后必须重新感知，比较“预期状态”和“真实状态”。

这正好对应赛题第 4 页的“看不清、看不懂、不会想”，以及第 7 页明确要求的“每步重新感知—比对预期—失败后生成修正序列”。题目甚至明确说机械臂动作本身可以不复杂，重点是感知、决策、闭环恢复和多智能体协同。

# 一、你对几个模型的判断，需要修正一点

## 1. Qwen3.8-27B 官方权重本身是多模态模型

官方模型卡把它定义为带视觉编码器的 Image-Text-to-Text 模型，并给出了 `image_url` 的 OpenAI 兼容调用示例。也就是说，你本地的 Qwen3.8-27B 理论上可以承担看图和规划。([Hugging Face][1])

假如你本地版本不能输入图片，大概率不是模型架构问题，而是以下某一层把视觉能力丢了：

* 下载的是裁剪后的纯文本 checkpoint；
* 量化包没有包含 vision tower；
* serving 框架只注册了文本模型；
* API 网关没有把 `image_url` 或图像 token 传给 processor；
* 内部接口虽然叫同一个名字，但实际映射到了文本部署。

因此本地 27B 不要立即淘汰。它很适合作为开发和离线兜底模型。

## 2. 你说的“开源 Max 没图像”基本是对的

公开的 Qwen3.8 大型 A95B 基础权重是文本生成模型；官方托管的 Max 服务才额外提供视觉等生产能力。因此赛题方部署的“开源 Qwen3.8 Max”若基于公开权重，确实很可能只能吃文本。([Hugging Face][2])

但这并不妨碍它当规划器，因为规划器不应该直接看原始图像，而应该读取结构化世界状态。

## 3. Qwen3.8-Flash-Next 很适合作为第一候选

官方公开版本属于原生多模态 MoE，并支持常见的 OpenAI 兼容部署方式。假如赛题方的 `qwen3.8flash` 确实映射到这一版本，它很适合做：

* 图像语义理解；
* 局部目标裁剪识别；
* 指令理解；
* JSON 目标生成；
* 失败原因分析；
* 必要时的重规划。([GitHub][3])

但不要仅凭内部别名判断，必须对实际 endpoint 做能力探针。

## 4. Kimi K3 也应进入实测候选

Kimi K3 官方定位是原生多模态长上下文模型，因此理论上也适合图像、工艺文档和长历史联合推理。([Moonshot][4])

不过内部开源部署的量化精度、视觉预处理、并发限制和推理框架，可能比模型名称更影响结果。因此最终选择必须靠你们自己的测试集，而不是参数规模或官方宣传。

## 我建议的模型分工

| 角色         | 第一选择                     | 备用或升级路径                      |
| ---------- | ------------------------ | ---------------------------- |
| 本地开发、离线演示  | Qwen3.8-27B 多模态          | 固定版本，保证可复现                   |
| 快速视觉语义入口   | Qwen3.8-Flash-Next       | Kimi K3                      |
| 高难规划、全局重规划 | 开源 Qwen3.8 Max，输入结构化世界状态 | Kimi K3 / Flash              |
| 实时执行控制     | 不使用大模型                   | MoveIt、RMPFlow、Isaac Sim 控制器 |
| 正常执行中的失败恢复 | 行为树本地规则                  | 连续失败后再调用大模型                  |

最稳妥的主线是：

> **Flash 负责视觉与日常规划，Max 只在复杂规划和多机器人调度时升级调用，27B 保留为本地基线和断网兜底。**

如果两模型方案来不及稳定，直接使用 Flash 或 27B 一模到底，也比勉强拼接多个模型更可靠。

# 二、工业界真正采用的不是“LLM 直接控机械臂”

目前比较成熟的工业思路普遍是：

1. 机器人能力先被封装成确定性的 Skills；
2. 行为树或工作流负责组织 Skills；
3. 视觉和传感器持续更新环境状态；
4. 大模型位于任务解释和异常决策层；
5. 安全控制、碰撞限制、速度限制独立于大模型。

Intrinsic Flowstate 的公开架构就是通过能力、技能、行为树来组织机器人过程，行为树承担控制流和失败恢复，底层连接感知、运动规划和硬件接口。Siemens 的工业 Copilot 同样更接近“人机交互和任务编排层”，而不是让语言模型绕过控制器直接产生伺服命令；安全能力也被放在独立层。([Intrinsic][5])

所以你们应该做：

> **强多模态模型 + 专用工业感知 + 有限技能库 + 确定性执行器**

而不是“强模型 + 弱模型”两个聊天机器人互相讨论，也不是“大模型 + VLA”就自动变成智能体。

# 四、感知模块应该怎么设计

这道题里的视觉不是普通“检测一下螺丝刀”就够了。评委给出的场景是密集、高反光、同类零件多、会倒放和倾倒。

因此感知结果至少要回答五件事：

1. 有多少个独立实例；
2. 它们分别是什么或最接近什么；
3. 它们在机器人基坐标系中的位置；
4. 它们是正常、倒放还是倾倒；
5. 当前判断有多大把握。

## 推荐感知链

### 1. RGB-D 或多视角输入

尽量使用 RGB-D，而不是只靠单目 RGB。深度可以帮助：

* 区分相互贴近的实例；
* 判断堆叠关系；
* 求取点云和位姿；
* 验证物体是否已经被抓起；
* 判断箱格是否被占用。

### 2. 候选实例提取

先由通用检测/分割模型产生实例 mask，但只把它当“候选生成器”，不要直接把开放词汇标签当最终真值。

赛题第 3 页已经展示了通用开放域检测会把多个工业部件合成一个整体，或者只得到“工业零件”“刀具”这种没法执行的粗粒度标签。

### 3. 视觉原型记忆

工业零件往往名称冷门、外形相似，纯文本 prompt 很难。更实用的做法是为每种零件保存：

* 5～20 张参考裁剪图；
* 不同角度的 CAD 渲染图；
* canonical orientation；
* 对应料箱和工艺约束；
* 可抓取区域和禁抓区域。

新场景中先提取实例，再和视觉原型库做匹配。模型不确定时返回 `unknown_part_17`，而不是硬猜“轴套”或“刀柄”。

T-Rex2 等工作的重要启示就是：罕见、复杂对象仅靠文本提示不稳定，视觉提示和文本提示结合更适合开放世界识别。([arXiv][6])

### 4. 6D 位姿和状态判断

有 CAD 或多视角参考图时，可以使用 FoundationPose 一类方法估计和跟踪新物体的 6D 位姿，而不必为每个新物体单独重新训练完整位姿网络。([NVIDIA][7])

“正常、倒放、倾倒”最好由几何规则判定：

```text
零件当前旋转 R
    ↓
与标准位姿 R_canonical 比较
    ↓
考虑零件自身对称群
    ↓
normal / inverted / toppled
```

不要让 VLM 仅凭一张高反光图片独立判断姿态。VLM 可以做辅助判断，但几何位姿应作为主证据。

### 5. 不确定性触发主动感知

当出现以下情况时，不要立即规划抓取：

```text
实例分割重叠严重
身份匹配分数过低
位姿置信度不足
抓取点被遮挡
不同模块结论冲突
```

智能体应调用：

```text
move_camera(viewpoint_2)
capture_rgbd()
redetect()
refine_pose()
```

这会形成一个很好的竞赛创新点：**不确定时主动改变视角，而不是让模型继续猜。**

### 6. Isaac Sim 合成数据

利用 Replicator 随机化：

* 零件数量和位置；
* 正常、倒放、倾倒比例；
* 遮挡和堆叠；
* 金属度、粗糙度、反射；
* 光源方向和曝光；
* 相机位置、焦距和噪声；
* 背景和料箱颜色。

Isaac Sim 官方 Replicator 本身就面向场景、物体、传感器随机化和合成数据生成。([Isaac Sim Documentation][8])

# 五、必须建立“证据化世界模型”

大模型不应该每次重新看整张图，再凭记忆判断场景。

应该维护一个 Blackboard：

```json
{
  "scene_id": "frame_00428",
  "objects": [
    {
      "id": "part_17",
      "label": "shaft_A",
      "pose_base": [0.42, -0.18, 0.09, 0.0, 0.71, 0.0, 0.71],
      "state": "inverted",
      "region": "B",
      "graspable": true,
      "confidence": {
        "instance": 0.96,
        "identity": 0.78,
        "pose": 0.91,
        "state": 0.94
      },
      "evidence": [
        "rgb_camera_1",
        "depth_camera_1",
        "prototype_match:shaft_A:view_07"
      ]
    }
  ],
  "regions": {
    "A": {"part_count": 8},
    "B": {"part_count": 13}
  },
  "bins": [
    {"id": "bin_1", "capacity": 25, "occupied": 19}
  ],
  "robot": {
    "holding": null,
    "reachable_regions": ["A", "B"]
  }
}
```

这样即便 Max 是纯文本模型，它也能根据这个状态进行高质量规划。

世界模型还应该显式保存三类记忆：

* **语义记忆**：CAD、BOM、说明书、SOP、料箱规则；
* **视觉记忆**：零件参考图、标准姿态、多视角特征；
* **情景记忆**：执行过哪些动作、为何失败、上次怎么恢复。

所谓“反思”也不要设计成模型自由输出一大段文字，而应变成结构化失败事件：

```json
{
  "skill": "place_in_slot",
  "result": "failed",
  "failure_code": "POSE_OUT_OF_TOLERANCE",
  "expected": "upright(part_17)",
  "observed": "toppled(part_17)",
  "retry_count": 1
}
```

可解释性来自证据、状态差分、技能契约和日志，而不是要求模型公开一段不可验证的长思维链。

# 六、规划层：让大模型生成目标，不要直接生成机械臂程序

## 第一级：自然语言转 GoalSpec

用户说：

> “帮我把零件最多的区域装箱，倒着的先翻正，箱满后搬到左边。”

大模型输出：

```json
{
  "task": "pack_parts",
  "source_selector": {
    "metric": "part_count",
    "operation": "argmax"
  },
  "destination": "bin_1",
  "constraints": [
    "upright_before_place",
    "stop_when_bin_full"
  ],
  "after_completion": {
    "task": "transport_bin",
    "destination": "left_stack_area"
  }
}
```

这个阶段可以由 Flash、27B、Kimi 或 Max 完成。

## 第二级：确定性编译成行为树

大模型不能随意发明动作。系统只允许它使用技能清单：

```text
scan_scene
move_camera
select_object
pick
verify_grasp
reorient
place_in_slot
verify_place
transport_bin
request_clarification
```

然后由编译器形成：

```text
Sequence
├── ScanAndUpdateWorld
├── SelectRegion(argmax(part_count))
├── RepeatUntil(region_empty OR bin_full)
│   └── Fallback
│       ├── Sequence
│       │   ├── SelectReachablePart
│       │   ├── Pick
│       │   ├── VerifyGrasp
│       │   ├── ReorientIfNeeded
│       │   ├── PlaceInFreeSlot
│       │   └── VerifyPlace
│       └── Sequence
│           ├── MoveCamera
│           ├── Redetect
│           ├── SelectAlternativeGrasp
│           └── Retry
├── TransportBin(left_stack_area)
└── VerifyGoal
```

SayCan 的核心思想是让语言模型的语义选择与机器人技能的实际可行性共同决定下一动作；ProgPrompt 则说明只向模型提供当前环境中的对象、可用动作和程序化约束，比自由文本生成更可靠。([SayCan][9])

行为树尤其适合这个赛题，因为它天然支持：

* 条件判断；
* fallback；
* 重试；
* 中断；
* 局部恢复；
* 运行时状态可视化。

LLM-BT 等工作也采用语义地图、语言规划和可动态更新的行为树来处理环境扰动。([arXiv][10])

一项 2025 年 IROS 工作进一步采用了“多模态状态抽取—LLM 生成 PDDL 问题—行为树执行”的结构，并报告了长时程操作任务上的较高成功率，这与这里的推荐方向基本一致。

# 七、闭环恢复要分成两层

这是你们系统最应该重点展示的部分。

## 内层：确定性局部恢复

普通失败不调用大模型：

| 失败码                     | 本地恢复           |
| ----------------------- | -------------- |
| `TARGET_OCCLUDED`       | 移动相机、重新感知      |
| `GRASP_EMPTY`           | 换抓取候选、再次抓取     |
| `OBJECT_DROPPED`        | 搜索掉落区域、重新定位    |
| `POSE_OUT_OF_TOLERANCE` | 重新抓取、调整姿态、再次放置 |
| `SLOT_OCCUPIED`         | 选择其他空格         |
| `IK_UNREACHABLE`        | 换抓取方向或切换机械臂    |

这种恢复快、稳定、可复现。

## 外层：大模型全局重规划

只有以下情况才重新调用大模型：

* 连续多次局部恢复失败；
* 用户中途改变目标；
* 原目标已经不可行；
* 出现未见过的失败类型；
* 多机器人资源冲突；
* 需要重新决定任务优先级。

输入给大模型的不是一堆视频帧，而是：

```text
原始目标
当前世界状态
计划执行位置
失败事件
已尝试的恢复动作
当前可用技能
```

Inner Monologue 等工作表明，成功检测、对象状态、场景描述和人类反馈等闭环信息能够显著增强语言规划器的执行和重规划能力。([Inner Monologue][11])

这也正是赛题要求的“每步重新感知—与预期比对—失败后自主生成修正任务序列”。

# 八、多智能体不要做成“多个大模型聊天”

赛题里的多智能体更合理的定义是：

* 机械臂 A；
* 机械臂 B；
* 搬运机器人 C；
* 共享世界模型和任务黑板；
* 每台机器人拥有自己的局部行为树。

中央协调器负责：

```text
任务分配
料箱和区域资源锁
抓取区域互斥
搬运时机
任务优先级
死锁检测
```

例如：

```text
Robot A → 区域 A 装箱
Robot B → 区域 B 装箱
Robot C → 搬运第一个完成的料箱
```

当 A 先完成后：

```text
C 锁定并搬运 A 的料箱
A 领取区域 D
B 继续区域 B
```

对于严格的前后顺序、共享设备和资源冲突，不要完全相信 LLM 自由调度。可以由 LLM产生任务和约束，再交给确定性调度器或约束求解器。近期 IMR-LLM 的工业多机器人方案也是让 LLM 辅助构建任务图，再用确定性方法求出可行计划，而不是让语言模型直接控制所有机器人。([arXiv][12])

# 九、VLA 在这个项目里不应该成为主线

OpenVLA 这类模型是“图像 + 指令 → 连续机器人动作”的通用策略模型，其公开版本使用了约 97 万条机器人操作轨迹训练。([Hugging Face][13])

你们的赛题却明确允许抓取、放置、搬运这些动作比较简单，重点考查：

* 工业目标感知；
* 指令理解；
* 复杂任务规划；
* 动态闭环；
* 失败恢复；
* 多智能体协同。

因此现在训练 VLA 的投入产出比很低，还会带来：

* 数据量不足；
* 仿真动作域适配；
* 连续控制不稳定；
* 中间状态不易审计；
* 很难证明创新到底来自哪里；
* 与已有确定性抓取和规划器重复建设。

更合理的定位是：

> 将来把 VLA 封装为某一个复杂技能，例如 `reorient_part_vla()`，但整个智能体仍然由世界模型、行为树和验证器管理。

类似 GR00T 的双系统架构也是慢速视觉语言推理负责理解和规划，快速动作系统负责执行。你们的快速动作系统完全可以先用传统控制器和技能原语，不一定非要训练一个 VLA。([NVIDIA Investor Relations][14])

# 十、模型 API 要加一层 Gateway

代码里绝对不要直接写死：

```python
call_qwen_flash(...)
call_kimi(...)
```

应该统一成：

```text
ModelGateway.generate(
    role="planner",
    messages=...,
    images=...,
    schema=GoalSpec
)
```

每个内部模型登记能力：

```json
{
  "name": "internal-qwen3.8-flash",
  "supports_vision": true,
  "supports_json_schema": true,
  "supports_tool_call": true,
  "max_context": 262144,
  "timeout_seconds": 20,
  "priority": 1
}
```

Gateway 负责：

* 视觉能力检测；
* JSON 解析和自动修复；
* 超时；
* 重试；
* 主备切换；
* 请求缓存；
* 输入输出日志；
* 模型版本记录；
* 同一任务跨模型 A/B 测试。

## 对内部 endpoint 必须做四类探针

### 视觉真实性探针

同一问题分别传入：

1. 真实场景图；
2. 全黑图；
3. 打乱图；
4. 不传图。

要求回答明确可验证的问题，例如零件数量、箱子颜色、倒放实例编号。若四种输入输出几乎一致，说明图像可能根本没传进模型。

### 结构化输出探针

重复运行指令转 GoalSpec，测：

* JSON 合法率；
* schema 通过率；
* 是否添加不存在字段；
* 是否生成不存在技能。

### 工业视觉探针

使用你们自己的图像测试：

* 实例计数；
* 正常/倒放/倾倒；
* 密集遮挡；
* 高反光；
* 未知目标拒识；
* 多目标关系，如最左、最多、最近。

### 恢复规划探针

给定结构化失败事件：

```text
抓取为空
放置倾倒
目标被遮挡
箱格已满
原目标不可达
```

检查模型能否只使用合法技能生成修正计划。

最终不要直接问“哪个模型最好”，而是比较：

```text
视觉状态准确率
GoalSpec schema 通过率
非法技能率
不存在对象幻觉率
计划前置条件违反率
恢复计划有效率
P50/P95 延迟
超时率
```

# 十三、开发优先级

## P0：先让主闭环成立

* 固定 `WorldState`、`GoalSpec`、`SkillCall`、`FailureEvent` 四个 schema；
* 实现行为树执行器；
* 封装 8～12 个基础技能；
* 每个技能都有前置条件、预期效果、验证器和恢复路径；
* 用本地 Qwen3.8-27B 跑通完整流程。

## P1：解决工业感知

* 实例 mask；
* RGB-D 坐标；
* 视觉原型检索；
* FoundationPose 或其他位姿模块；
* 正常/倒放/倾倒几何判定；
* 不确定性触发主动换视角。

## P2：接入赛题方 API

* Flash、Kimi、Max 全部走 Model Gateway；
* 运行固定小测试集；
* 根据实际结果确定默认模型和升级模型；
* 保留本地 27B 兜底。

## P3：做出评委能看懂的失败恢复

至少固定演示三种：

```text
抓空 → 换抓取点
放歪 → 重新抓取并摆正
目标遮挡 → 移动相机重新观察
```

## P4：再增加多机器人

使用共享 Blackboard、资源锁和确定性调度，不需要再增加几个互相聊天的 LLM Agent。

## 最终技术路线

**Qwen3.8-Flash-Next 或本地 Qwen3.8-27B 作为多模态语义入口；开源 Max 作为可选的文本高阶规划器；RGB-D、视觉原型和 6D 位姿模块建立可信世界状态；大模型只生成 GoalSpec；确定性编译器将其变成行为树；有限技能库负责执行；每个技能完成后重新感知并验证；普通失败本地恢复，连续失败才调用大模型重规划；VLA只保留为未来可插拔的复杂技能。**

这条路线既比“单一大模型直接控机械臂”可靠，也比“堆一堆 Agent 和模型”更容易完成、解释和评测，而且与赛题要求和工业方案高度一致。
